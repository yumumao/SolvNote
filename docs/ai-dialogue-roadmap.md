# AI解题多轮问答：下一阶段计划

状态：需求已提出，尚未实现。本次只更新说明与计划，不随当前镜像提供多轮问答入口。

## 已确认的目标

- 同一道题的AI解题过程支持多轮问答，而不是只能获得一次结果。
- 默认上限为10轮。
- 管理员可以修改默认轮数。
- 达到上限时先提示；管理员可以点击确认继续更多轮对话。
- 不自动无限续聊，不通过刷新或重试绕过上限。

## 建议的实现边界（实施前确认）

1. 以用户主动追问、AI回复为基本交互，不直接做无人值守的模型自我循环。下一阶段先确认是否还需要多模型自动讨论，两者的交互、费用和终止条件不能混用。
2. 建议一条已提交问题及其AI回复算一轮；首次解题是否计入10轮，实施前确认。提供明确的已用/上限显示。
3. 默认轮数由管理员在服务端设置并持久化。建议新会话记录创建时的额度快照，避免修改全局默认值时静默扩大或缩减所有历史会话。
4. 到限后服务端拒绝新调用，界面提示轮次、后续上下文增长和可能费用；普通用户不能绕过，管理员确认后只追加明确轮数。每次追加多少、是否允许管理员手动输入，实施前确认。
5. 上限检查、预留轮次和提交任务在同一事务中完成；并发标签页、重复提交、刷新、重试不能重复计费或绕过上限。内部供应商回退/复核不是用户新问答轮次，仍受既有调用预算约束。
6. 复用持久AI任务与取消、幂等和结果未知状态。失败/取消/未知是否退还轮次要按任务受理状态区分，不能承诺结果未知时一定未计费或自动重发。
7. 同题会话保留必要题图与人工修正条件，支持文字与多模态模型按能力调用。长会话需限制上下文长度和图片体积；摘要不能无提示丢掉几何条件或改写题目事实。
8. 会话、消息、额度、续聊审批与任务由服务端保存，校验用户/题目归属。管理员的配置或续聊能力不自动意味着可读取所有用户的题目与对话；权限范围先确认。
9. SQLite继续放在`/app/data`，加密主钥继续放在`/app/config`；备份与迁移沿用双卷配对原则。会话保留时长、删除与敏感上下文加密策略在数据模型设计时一并决定。
10. 正确解题优先，年级仍只是讲解偏好。不得因为轮数将尽强行声称答案正确；给出不确定点并让用户人工核对。

## 建议实施顺序

1. 明确轮次口径、首次解题计数、续聊追加规则、管理员可操作范围和全局默认值适用时机。
2. 设计会话/消息/轮次额度数据结构、迁移、服务端权限与并发控制，并编写失败用例。
3. 接入现有持久任务和多模态调用，再做同题追问UI、轮次提醒、管理员设置与确认续聊。
4. 使用合成题图及mock AI验证权限、10轮封顶、并发、续聊、重启恢复、取消/未知、题图上下文和费用提示。
5. 本地人工验收后再决定上线；真实题目外发及真实供应商费用测试单独确认。

## 验收重点

- 第10轮与第11轮边界准确；默认轮数修改、管理员追加的效果明确可见。
- 未授权用户不能改默认值或扩额；重放/并发不能多放行一次调用。
- 新旧题目和会话之间不串图、不串文本、不串权限。
- 超时、进程重启、重复点击不会静默丢会话或重复创建收费请求。
- README明确区分已经交付的功能与本计划，未验收前不写成可用特性。
